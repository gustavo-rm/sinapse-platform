# Prompt 06 — Core integration, generation job and orchestration

**Prerequisite:** prompts 01 to 05 complete and verified.
**Scope:** `coreclient` module, generation job execution, snapshot assembly and
`planning.orchestration`.
**Out of scope:** the optimisation algorithm itself, which lives in the Sinapse Core
repository. Do not implement, reimplement or approximate it. If the core is unavailable,
build against the contract and a stub — do not write a fallback that generates plans.

Read `CLAUDE.md`, section 9 of `docs/ARQUITETURA_BACKEND_SINAPSE.md` and
`docs/adr/0002-integracao-sinapse-core.md` and
`docs/adr/0007-contrato-do-core-e-reprodutibilidade.md` before starting.

---

## Task

### 1. Contract

Input: horizon, availability windows, goals with deadline and priority, topics with subject
and estimated effort, prerequisite edges with `strength` and `provenance`, session history
per topic, algorithm parameters, random seed.

Output: planned sessions with topic, start, duration and kind; fitness metrics; execution
metadata (core version, seed, generations, elapsed time).

DTOs only, in a package that could be extracted into a shared versioned artifact later.
No JPA annotations, no dependency on any module's internal classes.

### 2. Product parameters — decided, do not re-derive

See ADR 0012.

- **Horizon:** fixed 4 weeks, configurable. The goal's target date goes into the snapshot as
  a prioritisation constraint, never as the horizon.
- **Effort:** read `Topic.effortTier` and convert to minutes through the configured mapping.
  Then apply a per-student adjustment derived from the ratio of actual to planned duration
  across completed sessions. **Compute this during snapshot assembly; do not persist it.**
  It is derived data that would go stale and would need a table and a refresh job for no gain.
  A student with no history uses the unadjusted band value.
- **Catalogue revision:** record the current `catalog_import` id on the generation request.
  The snapshot carries the edges; only this records which curation state produced them, and
  the ablation experiment needs to attribute results to a catalogue revision.
- **Re-planning:** manual, triggered by the student. No automatic detection in v1.
- **Progress:** the job may expose an optional progress value. Null means indeterminate.
  Do not fabricate a percentage.

### 3. Orchestration

`planning.orchestration` is the only component in the system that knows more than one
context. It reads `curriculum`, `learningrecord` and `planning`, assembles the snapshot,
calls `coreclient`, and writes the resulting plan.

This is what breaks the cycle rule R2 would otherwise create. Do not move any of this logic
into `planning` itself, and do not inject a `learningrecord` service into `planning`.

### 4. Reproducibility — the point of this prompt

The job persists four things, not one: `snapshot`, `coreVersion`, `algorithmParams`,
`randomSeed`.

The genetic algorithm is stochastic. The same snapshot with the same parameters produces a
different plan unless the seed is fixed. All four are required for a plan to be
reproducible, and reproducibility is a thesis requirement.

`snapshot` stores the **exact payload sent**, serialised once and persisted as JSONB. Do not
reassemble it from the entities at read time; that would not be the same document.

The seed is generated by the backend and sent to the core, not chosen by the core. The
backend must be able to replay.

**Required verification:** run a job, then re-run the core with the stored snapshot,
parameters and seed, and confirm the resulting plan is identical. Report the comparison. A
reproducibility guarantee that has never been exercised is not a guarantee.

### 5. Job execution

States: `PENDING`, `RUNNING`, `READY`, `FAILED`, `CANCELLED`.

The table is the queue. Claim rows with `SELECT ... FOR UPDATE SKIP LOCKED`. Do not add a
message broker.

- One non-terminal job per account, enforced by partial index. Surface a clear error, not a
  constraint violation, when a student requests a second one.
- Timeout, retry limit and backoff are configuration, not constants in code.
- A failed job records `failureReason` without exposing internal detail through the API.

**Required verification:** two workers running concurrently must not claim the same job.
Test with real concurrent connections, not sequential calls.

### 6. Endpoints

```
POST /study-plans/generation-requests      creates the job
GET  /study-plans/generation-requests/{id} job state
GET  /study-plans/{id}                     the plan, once READY
```

The job creation endpoint returns immediately. It must never block waiting for the core.

Requesting generation requires `canProcessLearningData` from `AccountAccessPolicy`.

### 7. Failure modes

The core is a separate process over HTTP. Handle timeout, unavailability, malformed
response and partial response in `coreclient`. A core failure marks the job `FAILED`; it
must never corrupt the active plan or leave a partial plan persisted. Plan writing is one
transaction.
